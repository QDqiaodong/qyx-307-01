## 优化落地批次会签（现场经理口径：两步会签都点头，场景才允许切成推演后方案）

入口：前端顶部导航「落地批次」（`/batches`）。优化推演页跑完一轮也会给出直达链接。

- **每轮推演必冻批次**：执行优化推演的同一事务里，把这一轮冻成一份落地批次——逐区域钉死
  推演当时的**核定容量、编制配额、优化前分配、优化后分配**；之后区域档案怎么改都不回写，
  复查时对的就是这一份账。场景当前分配在推演后**一行不动**。
- **两步会签缺一不可**：测算岗确认数字（`POST /api/batches/{id}/confirm`）只推进批次状态，
  场景仍是旧方案；现场经理签收（`POST /api/batches/{id}/sign`）才会落地。
- **落地一笔事务两件事**：签收成功的同时，场景当前分配逐区域切成批次冻结的优化后方案，
  与批次置为 `APPLIED` 同事务提交——不会出现「批次落地了场景没改」或「场景改了没批次对账」。
  已落地的批次再进场景页，看到的仍是那套优化后数字。
- **轮次作废**：测算确认（或待确认）期间又跑了新一轮推演，旧批次立即进入 `STALE`，
  测算确认一并作废；现场经理再拿旧批次签收返回 409 `BATCH_STALE`，报文点名
  **哪一份批次、它冻的是哪一轮、场景当前已跑到哪一轮**（`data.batchId / frozenRunSeq / currentRunSeq`）。
- **封区守卫**：批次涉及的区域在签收时处于临时封区生效状态，整单拒绝落地（409
  `BATCH_BLOCKED_AREA_CLOSED`），先解封或作废封区单再签收。
- **并发只落一次**：确认/签收/推演都对场景行加悲观写锁串行化，同一份批次并发签收只成功一次，
  另一方收到 409 `BATCH_ALREADY_APPLIED`。

### 批次接口
| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/batches?scenarioId=` | 批次列表：冻结轮次、会签进度、逐区域冻结快照、作废原因 |
| GET | `/api/batches/{id}` | 批次详情 |
| POST | `/api/batches/{id}/confirm` | 测算岗确认（`{operator}`），场景分配不动 |
| POST | `/api/batches/{id}/sign` | 现场经理签收并落地（`{operator}`），同事务切场景 |

推演接口 `POST /api/scenarios/{id}/optimize` 的响应新增 `runSeq`（第几轮推演）与
`batchId`（本轮冻成的落地批次）。

### 数据表
- `optimization_batch`：批次头（状态 `PENDING_CONFIRM / CONFIRMED / APPLIED / STALE`、
  冻结轮次、会签人/时间留痕、作废原因、整体效果数字）。
- `optimization_batch_item`：逐区域冻结快照（不可变）：核定容量、编制配额、优化前/后分配。
- `flow_scenario` 新增 `current_run_seq`（当前第几轮推演）、`applied_run_seq`（当前分配落地的是第几轮方案）。

## 临时封区回灌（安全岗口径：回灌落不成账，绝不能关区）

入口：前端顶部导航「临时封区」（`/closures`）。

- **一笔事务、两件事一次做完**：提交封区时，被封区域在该场景的人员分配与客流分配同时清 0，
  清出来的人员/客流按各开放区域**当时剩余编制配额、剩余容量**用最大余数法拆到至少一块仍开放区域；
  任何承接区域回灌后都不超过核定容量/编制。
- **承接不下整单失败**：没有任何开放区域能完整吃下回灌时，只落一条 `FAILED` 回执，被封区域保持可营业、
  场景旧分配一行不动。回执写明：总缺口、逐块承接区域的剩余额度、卡在哪块、还差多少容量/编制、
  哪些剩余量被别的封区单占用。
- **封区生效封锁**：生效期间该区域不得作为负荷测算/优化推演的调入目标，也不能手工写回
  （`PUT /api/scenarios/{id}/allocation` 返回 409 `AREA_CLOSED`）。
- **并发只成一单**：提交对场景行加悲观写锁串行化。两人同时对同一场景封两块不同区域、回灌都指向
  同一块仅剩开放区域时，只允许一单成功落账，另一单失败并写明该开放区域剩余量已被别的封区单占用。
  单据持久化：关掉页面再打开，成功单仍生效，失败单不会自己变成成功。
- **额度冲突禁止解封**：承接区域核定容量/编制被改小、导致已生效封区单回灌数字超额时，
  回灌台账数字**不改写**，该封区单进入 `QUOTA_CONFLICT`（额度冲突、禁止解封），解封按钮不可用，
  直到值班长手工作废。
- **作废 vs 解封**：
  - 作废（`POST /api/closures/{id}/void`）：被封区域恢复可营业，但回灌到承接区域的人员/客流不自动撤回，
    以免和后续优化推演打架。
  - 解封（`POST /api/closures/{id}/reopen`，仅 `EFFECTIVE` 可用）：撤回本单回灌、把被封区域恢复到封区前快照。

### 封区接口
| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/closures` | 提交封区（`{scenarioId, areaId, reason}`），成功返回 `EFFECTIVE`，失败返回 `FAILED` 回执（HTTP 仍为 200） |
| GET | `/api/closures?scenarioId=` | 封区单列表：是否生效、回灌落到哪些开放区域、失败/冲突明细 |
| GET | `/api/closures/{id}` | 单据详情 |
| POST | `/api/closures/{id}/void` | 值班长作废（回灌保留） |
| POST | `/api/closures/{id}/reopen` | 正常解封（撤回回灌） |

### 数据表
- `area_closure`：封区单（状态 `EFFECTIVE / FAILED / QUOTA_CONFLICT / REOPENED / VOIDED`、疏散快照、失败回执 JSON、额度冲突 JSON）。
- `closure_injection`：回灌台账（不可变）：每块承接区域分到的人员/客流、落账前占用、当时剩余额度。
