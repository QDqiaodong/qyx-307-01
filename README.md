## 推演落地批次（两段会签口径：两步都点头，场景才允许改方案）

入口：前端顶部导航「优化推演」（`/optimization`）执行推演，「落地会签」（`/batches`）走会签。

- **推演只冻账，不改场景**：每执行一轮优化推演，就在同一事务冻出一份**落地批次**，冻住当时每块区域的
  核定容量、编制配额、优化前分配、优化后分配（之后额度被改小也不改写批次数字）。推演只产出新轮次草稿，
  场景在用分配一行不动，屏幕上的优化数字不等于已经按新方案排人。
- **两段会签闸门**（按现场经理口径）：
  1. **测算岗确认数字**（批次 `DRAFT -> CONFIRMED`）：只改批次状态；
  2. **现场经理签收**（`CONFIRMED -> LANDED`）：签收成功的**同一笔事务**才把场景当前人员/客流分配
     改成批次冻住的优化后方案。测算确认之后、现场签收之前，场景分配必须仍是旧方案。
- **新轮作废**：测算确认后如果又跑了一轮新推演，上一轮在途批次（含已确认未签收）一律 `SUPERSEDED`，
  现场经理不能再拿旧批次改场景；签收旧批次返回 409，回执写清是**哪份批次、冻的是哪一轮、场景现在哪一轮**。
- **落不了整单拒绝**：签收时若优化后目标区域正处于封区生效、或冻住的优化后数字已超当前核定容量/编制，
  整单 409 失败、场景旧方案一行不动。
- **持久可对账**：批次/明细只追加不物理删除；已会签落地的批次是终态（再跑新推演也不作废），
  再进场景页分配仍是那一套优化后数字，并标明来自哪份批次。

### 批次接口
| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/scenarios/{id}/optimize` | 执行第 N 轮推演：轮次 +1、作废旧轮在途批次、冻出落地批次（响应含 `optimizationRound`、`batchId`），场景在用分配不变 |
| GET | `/api/batches?scenarioId=` | 批次台账：冻的轮次、会签状态、每块区域冻结档案、作废回执 |
| GET | `/api/batches/{id}` | 批次详情 |
| POST | `/api/batches/{id}/confirm` | 测算岗确认数字（第一步，不改场景） |
| POST | `/api/batches/{id}/sign` | 现场经理签收（第二步，同事务把场景改成优化后方案） |

### 数据表
- `optimization_batch`：批次头（状态 `DRAFT / CONFIRMED / SUPERSEDED / LANDED`、冻结轮次、推演概览、两段会签时间/备注、作废原因）。
- `optimization_batch_item`：逐区域冻结明细（不可变）：核定容量、编制配额、优化前人员/客流、优化后人员/客流。
- `flow_scenario` 增列 `optimization_round`：场景当前已执行到的推演轮次；`staff_allocation` 草稿行随轮冻住前后快照。

## 临时封区回灌（安全岗口径：回灌落不成账，绝不能关区）

入口：前端顶部导航「临时封区」（`/closures`）。

- **一笔事务、两件事一次做完**：提交封区时，被封区域在该场景的人员分配与客流分配同时清 0，
  清出来的人员/客流按各开放区域**当时剩余编制配额、剩余容量**用最大余数法拆到至少一块仍开放区域；
  任何承接区域回灌后都不超过核定容量/编制。
- **承接不下整单失败**：没有任何开放区域能完整吃下回灌时，只落一条 `FAILED` 回执，被封区域保持可营业、
  场景旧分配一行不动。回执写明：总缺口、逐块承接区域的剩余额度、卡在哪块、还差多少容量/编制、
  哪些剩余量被别的封区单占用。
- **封区生效封锁**：生效期间该区域不得作为负荷测算/优化推演的调入目标，也不能手工写回
  （`PUT /api/scenarios/{id}/allocation` 返回 409 `AREA_CLOSED`）。
- **并发只成一单**：提交对场景行加悲观写锁串行化。两人同时对同一场景封两块不同区域、回灌都指向
  同一块仅剩开放区域时，只允许一单成功落账，另一单失败并写明该开放区域剩余量已被别的封区单占用。
  单据持久化：关掉页面再打开，成功单仍生效，失败单不会自己变成成功。
- **额度冲突禁止解封**：承接区域核定容量/编制被改小、导致已生效封区单回灌数字超额时，
  回灌台账数字**不改写**，该封区单进入 `QUOTA_CONFLICT`（额度冲突、禁止解封），解封按钮不可用，
  直到值班长手工作废。
- **作废 vs 解封**：
  - 作废（`POST /api/closures/{id}/void`）：被封区域恢复可营业，但回灌到承接区域的人员/客流不自动撤回，
    以免和后续优化推演打架。
  - 解封（`POST /api/closures/{id}/reopen`，仅 `EFFECTIVE` 可用）：撤回本单回灌、把被封区域恢复到封区前快照。

### 封区接口
| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/closures` | 提交封区（`{scenarioId, areaId, reason}`），成功返回 `EFFECTIVE`，失败返回 `FAILED` 回执（HTTP 仍为 200） |
| GET | `/api/closures?scenarioId=` | 封区单列表：是否生效、回灌落到哪些开放区域、失败/冲突明细 |
| GET | `/api/closures/{id}` | 单据详情 |
| POST | `/api/closures/{id}/void` | 值班长作废（回灌保留） |
| POST | `/api/closures/{id}/reopen` | 正常解封（撤回回灌） |

### 数据表
- `area_closure`：封区单（状态 `EFFECTIVE / FAILED / QUOTA_CONFLICT / REOPENED / VOIDED`、疏散快照、失败回执 JSON、额度冲突 JSON）。
- `closure_injection`：回灌台账（不可变）：每块承接区域分到的人员/客流、落账前占用、当时剩余额度。
